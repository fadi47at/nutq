> هذه الوثيقة خطة عمل، لا وصفًا للواقع. كل بند "موجود حاليًا" تم التحقق منه في
> جولة تدقيق بتاريخ هذه الوثيقة (نسخة التطبيق وقتها: v0.7.2).

### نقاط القوة المنتَجية (ما يميز البرودكت)

1. **خط أنابيب من مرحلتين** (تفريغ ثم تنقيح) — قابل للتشخيص وللتوسيع.
2. **حيادية تجاه المزودين**: Gemini / Claude / ElevenLabs / أي endpoint متوافق مع
   OpenAI — وهذا هو المفتاح التجاري القادم (انظر §3).
3. **الخطوط (Lines)**: كل خط = اختصار + وضع معالجة + وجهة — مفهوم منتج واضح.
4. **وضع Spec** (فكرة منطوقة → موجز جاهز لوكيل برمجي) — ميزة بيع حقيقية لا
   يملكها كل تطبيق إملاء.
5. **موثوقية الـ pill** (watchdog + سجل overlay.log) — هندسة صلبة نادرة في MVP.
6. **التاريخ + إعادة التوليد + الملاحظات + المهام** — البرنامج يتجاوز "الإملاء"
   إلى نظام إنتاجية صوتي.

## 2. القرار المعماري المفتاح (قبل أي كود)

**وعد الخصوصية الحالي يقول: "الصوت لا يلمس القرص".** عندما نضع سيرفر وسيط
(نحن نملك المفاتيح ونوزع التوكنز) سيمر الصوت أو النص عبر سيرفراتنا. يجب
البت في واحدة من ثلاث:

- **(أ) بوابة صوتية كاملة**: الصوت يمر عبر سيرفرنا إلى المزود. أبسط هندسيًا،
  لكنه يكسر وعد الخصوصية — يتغيّر التسويق ويُكتب صراحة.
- **(ب) بوابة نصية فقط (موصى بها كخطوة أولى)**: التفريغ (STT) يبقى من حساب
  المستخدم أو عبر مزود STT رخيص، والتنقيح يمر عبر بوابتنا. حل وسط.
- **(ج) BYOK + اشتراك للقيمة المضافة**: الاشتراك يفتح الميزات (خطوط غير
  محدودة، ثيمات، Spec mode…) والمفاتيح تبقى لدى المستخدم. أسرع طرحًا، ربح
  أقل.

**التوصية: نبدأ بـ (ج) لأنها صالحة للطرح خلال أسابيع، ونبني (ب/أ) بالتوازي
كـ "nutq Cloud" مع خطة اشتراك.** البنية الحالية تساعدنا: التطبيق أصلاً يقبل
custom base URL لكل مرحلة، فتوجيهه إلى `api.nutq.app` لاحقًا = تغيير إعدادات
لا إعادة كتابة.

### تفصيل تقسيم `lib.rs` (من المرحلة 0)

الملف (~81KB، ~2200 سطر) يحوي خمس عناقيد واضحة، لكل منها موديول:

| الموديول الجديد | المحتوى الحالي في lib.rs |
|---|---|
| `overlay.rs` | Status, OverlayWatch, place_overlay, ensure_topmost/no_activate, spawn_overlay_watchdog, build_overlay, spawn_level_ticker, overlay_* commands |
| `commands.rs` | get/update_settings, set_api_key, key_status, history commands, usage/stats, todos/notes/logs commands |
| `pipeline.rs` | toggle, toggle_recording, cancel_recording, park, stt/refine_backup_cfg, file_note, emit_warning/error |
| `hotkeys.rs` | parse_hotkey, arm/disarm_escape, register_hotkeys, bind, spawn_hotkey_retry, retry_unbound_hotkeys |
| `lib.rs` (يبقى) | run(), build_tray(), AppState — نقطة التجميع فقط |

القاعدة: نقل بلا تغيير سلوك، سطر بسطر، ويُختبر بعد كل نقل بـ `cargo check &&
cargo test`. ممنوع دمج النقل مع أي ميزة جديدة في نفس الـ commit.

## 2-ملاحقة. التدقيق التصميمي (ملخص — التفصيل في `design-proposals/report.md`)

أجراه تدقيق مستقل (سب أيجنت) على نظام التصميم والواجهات والـ landing. أبرز النتائج:

**قوة التصميم مؤكدة**: نظام التوكنز الثلاثي الطبقات نموذجي، `Kbd` keycaps مميز،
اتساق الأيقونات والـ PageHead في كل الصفحات (6/6)، والـ overlay قطعة متقنة.

**ثلاث ملاحظات حرجة** (تدخل المرحلة 0/1):
1. تباين `--text-3` لا يجتاز WCAG AA (2.9:1 فاتح، 4.0:1 غامق) — إصلاح فوري.
2. `letter-spacing` على نصوص عربية يفكك الوصلات — طبقة label/eyebrow تحتاج بديلًا عربيًا.
3. `nutq-landing.html` بلا بنية HTML سليمة (لا doctype/meta/OG) — تعطل المشاركة والفهرسة.

**الهوية المقترحة**: "الهدوء الذي يكتب" — داكن أولًا، Teal الوحيد المتوهج،
توحيد الخطوط (Vazirmatn + Cascadia Mono) بين التطبيق والـ landing، والموجة
الصوتية كموتيف هوية. نموذج landing كامل في `design-proposals/landing-v2.html`.

## 4. توزيع التوكنز (تصميم أولي)

- **الوحدة المحاسبية**: "دقيقة صوت مفرّغة" و"1000 توكن تنقيح" — لا توكنز
  خام أمام المستخدم.
- **الخطة المجانية**: مثلاً 30 دقيقة/يوم تفريغ + 50 عملية تنقيح/يوم — كافية
  للتجربة، محفّزة للترقية.
- **Pro**: مقابل شهري ثابت + سقف عادل (fair use)، وشراء حزم إضافية (top-up).
- **الحماية من الإساءة**: حد معدل الطلبات لكل حساب، كشف الحسابات المتعددة
  بالإصبع التقني البسيط، تجميد الحسابات المخالفة.
- **هامش الربح**: الكلفة الفعلية (Gemini/Claude بالجملة) مقابل سعر الخطة —
  عدّاد الكلفة الحالي في التطبيق يعطينا الأرقام الحقيقية للاستخدام المحلي
  لاستنباط التسعير.

## 6. المنصات واللغة البرمجية: سطح المكتب، الماك، والموبايل

### القرار: نبقى على Tauri 2 + Rust + React/TypeScript

لا داعي لتغيير لغة البرمجة. الأسباب:

1. **Tauri 2 يبني لأندرويد وiOS من نفس المشروع** (منذ الإصدار 2.0) — نفس
   واجهة React ونفس كود Rust، بدل كتابة تطبيق ثالث من الصفر.
2. **قلب المنتج قابل للنقل كما هو**: خط الأنابيب (`stt.rs`, `refine.rs`,
   `net.rs`, `modes.rs`) والملاحظات والمهام كلها Rust عادي لا يعتمد على
   Windows. وحتى التسجيل (`cpal`) يعمل على Android وiOS.
3. **إعادة الكتابة (Flutter / React Native / Swift+Kotlin)** تعني رمي مسار
   مجرَّب ومحكَم (الاحتياطي، إعادة المحاولة، التشخيص) مقابل لا شيء يراه
   المستخدم. Electron أثقل بكثير ولا يضيف شيئًا.

ما **لا** ينتقل للموبايل، ولماذا لا مشكلة: الاختصار العام، واللصق في تطبيق
آخر، ومؤشر التسجيل العائم — هذه مفاهيم سطح مكتب. على الموبايل شكل المنتج
مختلف أصلًا: زر تسجيل كبير، ويدجت على الشاشة الرئيسية، Quick Tile في
أندرويد، وزر Action/Shortcuts في iOS، ومشاركة النص لأي تطبيق. المكافئ
الحقيقي لـ"الصق حيث تكتب" على الموبايل هو **لوحة مفاتيح مخصصة** (keyboard
extension في iOS / IME في أندرويد) — تحتاج كودًا أصليًا (Swift/Kotlin)
صغيرًا، ومكانها مرحلة لاحقة.

### الفكرة التي تميّز nutq: "خيوط الأفكار"

تطبيقات الإملاء (Wispr Flow, Superwhisper) تكتب ما تقول؛ تطبيقات الملاحظات
الصوتية (AudioPen, Voicenotes) تحفظه. لا أحد منهما **يُنمّي فكرة يومًا بعد
يوم**. الاقتراح:

- **الخيط**: فكرة واحدة لها اسم (مثلًا "تطبيق nutq للموبايل"). كل تسجيل
  جديد على خط "الأفكار" يُلحق بخيط موجود أو يبدأ خيطًا جديدًا.
- **المستند الحي**: بعد كل إضافة يعيد الذكاء الاصطناعي كتابة مستند الخيط:
  الخلاصة الحالية، القرارات، الأسئلة المفتوحة، الخطوة التالية — ويُظهر
  "ما الذي تغيّر منذ أمس".
- **التفكير بصوت عالٍ**: زر/اختصار "فكّر معي" يسجّل بلا هدف لصق، ويرتّب
  الكلام إلى نقاط، ويقترح ربطه بخيط قائم.
- البنية جاهزة جزئيًا: `notes.rs` + وضع Spec + صفحة الملاحظات. الخيط =
  ملاحظة لها سجل إضافات بدل نص واحد.

### الترتيب المقترح

1. ✅ واجهة عربية كاملة (v0.11.0).
2. **خيوط الأفكار على سطح المكتب** — الميزة التي تُباع، تُجرَّب أولًا حيث
   المنتج يعمل اليوم.
3. **macOS موقّع** — الـ CI يبني الـ dmg أصلًا؛ ينقص حساب Apple Developer.
4. **الحسابات + المزامنة** (المرحلة 2 أعلاه) — بدونها لا معنى لتطبيق موبايل
   يرى أفكار سطح المكتب.
5. **تطبيق الموبايل عبر Tauri 2** — أندرويد أولًا (نشر أسهل وأرخص)، ثم iOS
   (يحتاج جهاز Mac للبناء + حساب Apple). شاشة رئيسية = زر تسجيل + الخيوط.
6. لوحة المفاتيح الصوتية (iOS/Android) — آخر خطوة، كود أصلي.
